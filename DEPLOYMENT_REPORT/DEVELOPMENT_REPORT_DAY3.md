## 2. 핵심 개선 사항

### 구조화 주소 매칭 추가

주소 비교 로직을 문자열 유사도 중심에서 구조화 매칭 중심으로 보강했다. 기존에는 `부산광역시 연제구 토곡로 7`과 `부산광역시 연제구 토곡로 7 1층`처럼 같은 장소라도 층/호수 정보 때문에 유사도가 떨어질 수 있었다.

이번 변경으로 다음 정보는 검색과 매칭 과정에서 제거하거나 별도 처리한다.

- `1층`, `2층`, `지하 1층`
- `201호`, `1001호`
- `B1F`, `2F` 같은 층 표현

주소 매칭은 도로명, 번지, 동/읍/면/리, 우편번호 키를 추출해 비교한다. 구조화 키가 일치하면 주소 유사도를 `1.0`으로 처리할 수 있어, 실제 같은 장소를 더 안정적으로 자동 승인할 수 있다.

### 프랜차이즈 검증 규칙 보강

프랜차이즈 상호는 주소가 없는 경우 오승인 위험이 크다. 예를 들어 `스타벅스`, `빕스`, `이디야`처럼 지점이 많은 브랜드는 지점명이나 주소 없이 브랜드명만으로 특정 매장을 확정할 수 없다.

3일차에는 프랜차이즈 브랜드 사전을 추가하고 다음 규칙을 적용했다.

- 유명 프랜차이즈가 주소 없이 등장하고 지점 힌트가 없으면 자동 반려
- 지점명이 있으면 기존 네이버/인허가 검증 흐름을 계속 진행
- 주소가 있는 경우 같은 브랜드이고 구조화 주소가 일치하면 자동 승인 가능
- 브랜드명 변형을 별칭으로 인식

현재 반영된 브랜드 예시는 다음과 같다.

```text
스타벅스
빕스
투썸플레이스
이디야
빽다방
메가커피
컴포즈커피
맥도날드
롯데리아
써브웨이
파리바게트/파리바게뜨
본도시락
```

이 변경으로 프랜차이즈 데이터는 보수적으로 다루되, 주소나 지점 정보가 충분한 경우에는 자동 승인할 수 있게 되었다.

### 주소 없는 fuzzy 후보 자동 승인 조건 확장

Day2에서는 주소 없는 정확 일치 후보를 중심으로 자동 승인을 확장했다. Day3에서는 실제 데이터에서 발생하는 표기 차이를 고려해 fuzzy name matching을 추가했다.

자동 승인 가능한 예시는 다음과 같다.

- `예이제` → `예이제 해운대본점`
- `동진가셀프식당` → `동진가식육식당`
- `취원` → `취원 본점`
- `이디야 김해국제공항국제선점외 2` → `이디야커피 김해국제공항 국제선점`

다만 다음 조건에서는 자동 승인하지 않는다.

- 지점명이 충돌하는 경우
- 네이버 후보 주소가 부산이 아닌 경우
- 같은 주소에서 인허가가 폐업 상태로 확인되는 경우
- 상호가 너무 짧고 후보명에 포함되지 않는 경우

즉, 자동 승인 범위는 넓혔지만 지점 충돌, 지역 불일치, 폐업 신호는 계속 방어 조건으로 유지했다.

### 수동 피드백 기반 자동 반려 규칙 추가

관리자가 반복적으로 반려할 가능성이 높은 케이스를 규칙화했다. 예를 들어 법인명만 있고 실제 점포 정보가 부족하거나, 폐업/운영중단으로 판단된 상호는 API 호출 전에 자동 반려할 수 있다.

추가된 주요 반려 규칙은 다음과 같다.

- 법인명/상호만 있고 실제 매장 정보가 부족한 케이스
- 폐업 또는 운영중단으로 확인된 상호
- 결제대행사/카드사/지역화폐명으로 보이는 결제처
- `미상`, `불명`, `무기재` 같은 placeholder 이름과 주소가 후보 주소와 불일치하는 케이스
- 네이버 후보 카테고리가 `other`이고 지출 목적도 음식 소비 맥락이 아닌 케이스

이 규칙은 불필요한 외부 API 호출과 관리자 검토 부담을 줄이는 목적이다.

### 네이버 검색 쿼리 생성 개선

네이버 검색 쿼리 생성 로직이 크게 강화되었다. 기존에는 원본 상호와 주소를 단순 조합했지만, Day3에서는 실제 데이터의 노이즈를 처리하기 위해 여러 변형 쿼리를 생성한다.

개선 내용은 다음과 같다.

- `외 1`, `외 2개소`, `등` 같은 부가 표현 제거
- 괄호 안 지점 힌트 보존
- 주소에서 층/호수 제거 후 우선 검색
- 쉼표, 슬래시, 가운데점 기준으로 혼합 상호 분리
- 음식점으로 보이는 부분을 우선 검색
- 수동 검토에서 발견된 특정 alias 확장
- `카페가온비`, `궁꼬막한정식`, `푸짐한실비식당`, `예이제` 등 실데이터 기반 후보 쿼리 보강

이 변경은 네이버 후보 검색 실패율을 낮추기 위한 작업이다.

## 3. 파이프라인 개선

### 기존 성공 evidence 재활용

`verify_pending` 실행 시 이미 성공한 `place_verifications` evidence가 있으면 외부 API를 다시 호출하지 않고 해당 근거로 자동 승인할 수 있게 했다.

이로 인해 다음 상황을 처리할 수 있다.

- 과거에 성공 검증된 후보가 수동 검토 상태로 되돌아간 경우
- 재검증 대상이지만 provider evidence가 충분히 남아 있는 경우
- 네이버/인허가 API를 다시 호출할 필요가 없는 경우

단, `PERMIT_NOT_ACTIVE` 계열 사유가 있는 경우에는 기존 provider evidence가 자동으로 덮어쓰지 않도록 보호했다. 폐업/이전/비활성 인허가 신호는 여전히 보수적으로 처리한다.

### 여러 네이버 후보 evidence 저장

수동 검토로 이동하는 후보에 대해 선택된 1개 후보만 저장하지 않고, 최대 5개의 provider 후보 evidence를 함께 저장한다. 관리자 화면에서는 이 후보들을 비교하고 선택할 수 있다.

저장되는 주요 정보는 다음과 같다.

- provider place id
- 후보명
- 카테고리
- 지번 주소
- 도로명 주소
- 좌표
- 이름 유사도
- 주소 유사도
- 검증 상태와 reason code

이 변경으로 관리자는 단순히 “승인/반려”만 하는 것이 아니라, 후보 목록 중 올바른 네이버 장소를 선택해 승인할 수 있다.

## 4. 관리자 워크플로 개선

### provider 후보 선택 승인

수동 검토 화면에 네이버 후보 목록이 표시된다. 각 후보는 승인 가능 여부, 이름 유사도, 주소 유사도, 주소 정보를 함께 보여준다.

관리자는 radio 버튼으로 후보를 선택한 뒤 승인할 수 있다. 승인 시 선택한 provider 후보의 네이버 place id, 상호명, 카테고리, 주소, 좌표를 사용해 음식점 레코드를 만든다.

같은 `naver_place_id`가 이미 존재하면 신규 음식점을 만들지 않고 기존 음식점에 병합한다. 이로써 수동 승인으로 인한 중복 음식점 생성을 줄일 수 있다.

### 반려 사유와 검토 의견 저장

수동 반려 API가 `reason`과 `reviewer_note`를 받을 수 있게 확장되었다. 관리자 화면에는 반려 사유 select와 검토 의견 textarea가 추가되었다.

현재 UI에서 선택 가능한 반려 사유는 다음과 같다.

```text
수동 반려
법인명/정보부족
결제대행/카드명
폐업/운영중단
주소 불일치
지점 불명확
동일상호 과다
```

반려 사유와 검토 의견은 후보, 수동 검토 task, audit log에 저장된다. 이후 자동 규칙화하거나 운영 품질을 분석하는 데 사용할 수 있다.

### 검증 현황 리포팅 개선

관리자 화면의 최근 배치 요약에 `반려` 수치가 추가되었다. 수동 검토 목록은 최신 후보와 여러 provider 후보를 함께 보여주도록 확장되었다.

검토 화면 레이아웃도 단일 컬럼 중심으로 변경하고, 리뷰 신고 영역은 수동 검토 하단 섹션으로 정리했다.

## 5. 공개 사용자 기능 개선

음식점 상세 패널에 `네이버 지도에서 보기` 링크를 추가했다. 서버 응답에는 `naver_map_query`, `naver_map_url`이 포함된다.

지도 링크 생성 시 주소의 층/호수 정보를 제거하고, 상호명이 주소에 이미 포함되어 있으면 주소만 검색어로 사용한다. 이를 통해 네이버 지도 앱에서 더 안정적으로 장소 검색이 되도록 했다.

예시는 다음과 같다.

```text
토곡정 + 부산광역시 연제구 토곡로 7 1층
→ 토곡정 부산광역시 연제구 토곡로 7
```

## 6. 테스트 및 검증 결과

Day2 기준 전체 테스트는 30개였다. Day3 기준 전체 테스트는 63개로 확대되었고, 권한 밖 실행 기준으로 모두 통과했다.

```text
Ran 63 tests in 2.066s
OK
```

검증된 주요 케이스는 다음과 같다.

- 층/호수 제거 후 구조화 주소 매칭
- 주소 정제 후 자동 승인
- 주소 불일치 시 수동 검토 유지
- 음식 맥락이 없는 `other` 카테고리 자동 반려
- 주소 없는 fuzzy 상호 자동 승인
- 지점명 충돌 시 자동 승인 방지
- 부산 외 후보 자동 승인 방지
- 폐업 인허가 신호가 있는 후보 보호
- 프랜차이즈 주소 없는 후보 자동 반려
- 프랜차이즈 지점/주소 기반 승인
- 결제대행/카드명 자동 반려
- placeholder 상호와 주소 불일치 자동 반려
- 여러 네이버 후보 evidence 저장
- 기존 성공 evidence 기반 재검증 승인
- provider 후보 선택 승인
- 같은 네이버 place id 수동 승인 시 기존 음식점 병합
- 수동 반려 사유와 검토 의견 저장
- 네이버 지도 링크 검색어 생성

샌드박스 내부에서는 이전과 동일하게 HTTP 서버 테스트 2개가 `127.0.0.1` 임시 포트 바인딩 권한 문제로 실패한다. 동일 명령을 권한 밖에서 실행하면 전체 테스트가 통과하므로, 현재 확인된 실패 원인은 코드 문제가 아니라 실행 환경 제한이다.

## 8. 리스크 및 다음 과제

### 자동 승인 기준 운영 검증

fuzzy 상호 승인과 프랜차이즈 규칙은 테스트 케이스로 방어되어 있지만, 실제 라이브 데이터에서 오승인 비율을 확인해야 한다. 특히 지점명이 없는 유명 브랜드, 같은 상호의 여러 지점, 폐업/이전 인허가 신호는 표본 검수가 필요하다.

### 관리자 피드백 루프 정리

반려 사유와 검토 의견이 저장되기 시작했으므로, 다음 단계에서는 이를 집계해 자동 규칙 후보로 전환하는 흐름이 필요하다. 단, 잘못된 피드백이 alias memory나 자동 반려 규칙에 과도하게 반영되지 않도록 관리 기능이 필요하다.

### provider 후보 품질 확인

여러 네이버 후보를 저장하는 구조가 들어갔으므로, 후보 정렬 기준과 승인 가능 조건이 실제 관리자 검토에 충분한지 확인해야 한다. 필요하면 후보별 근거 표시를 더 명확히 해야 한다.

### 실서비스 배포 준비

현재 개발 DB와 테스트 기반은 안정화되고 있지만, 운영 배포 전에는 다음 항목이 필요하다.

- PostgreSQL/PostGIS 마이그레이션 적용 검증
- 실제 네이버/공공데이터포털 API 키로 라이브 배치 실행
- 배치 실패/재시도/수동 재검증 운영 절차 정리
- 관리자 계정 권한 모델 구체화
- alias memory 수정/삭제 관리 기능

## 9. 한 줄 결론

3일차 개발에서는 검증 파이프라인이 “자동 판정”을 넘어 “운영자가 근거를 보고 선택할 수 있는 검토 시스템”으로 확장되었다. 구조화 주소 매칭, 프랜차이즈 방어 규칙, 여러 provider 후보 저장, 수동 승인/반려 기록이 추가되면서 실제 공공데이터 운영에 필요한 신뢰성과 추적 가능성이 크게 강화되었다.
