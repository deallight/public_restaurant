# 공공기관 업무추진비 맛집 지도 서비스 개발 진행 보고서 2일차

작성일: 2026-06-05

## 1. 2일차 개발 요약

2일차 개발은 공개 화면 확장보다 데이터 검증 품질 개선에 집중했다. 1일차에는 부산 업무추진비 데이터를 수집하고 지도 서비스로 노출하는 MVP 골격이 완성되었다면, 2일차에는 실제 업무추진비 데이터에서 자주 발생하는 애매한 상호명, 지점명, 주소 누락, 비음식 지출을 더 안정적으로 처리하도록 검증 로직을 보강했다.

이번 변경의 기준 커밋은 다음과 같다.

```text

```

변경 규모는 총 6개 파일, 1,034줄 추가, 39줄 삭제다.

```text
app/agents.py          | 검증 규칙 및 이름/주소 매칭 개선
app/alias_memory.py    | 별칭 기억 기능 추가
app/integrations.py    | 네이버 검색 쿼리 정제
app/pipeline.py        | 별칭 기반 자동 승인 및 재검증 흐름 반영
app/services.py        | 검증 현황 및 수동 승인 별칭 저장 보강
tests/test_pipeline.py | 검증 회귀 테스트 대폭 추가
```

## 2. 핵심 개선 사항

### 별칭 기억 기능 추가

`alias_memory` 기능을 추가했다. 한 번 승인된 음식점의 원본 상호명과 네이버/정규화 상호명을 별칭으로 저장하고, 이후 같은 장소가 다시 등장하면 외부 API를 다시 호출하지 않고 기존 음식점에 연결할 수 있다.

예를 들어 주소가 없는 `두레박국밥` 행이 한 번 검증되어 지도에 노출된 뒤, 다음 배치에서 같은 상호가 다시 등장하면 `ALIAS_MEMORY_MATCH` 근거로 기존 음식점에 자동 연결된다.

이 기능으로 반복 등장하는 음식점의 검증 비용이 줄고, 동일 장소가 여러 음식점 레코드로 쪼개지는 문제를 완화할 수 있다.

### 주소 없는 음식점 후보 처리 개선

1일차에는 주소가 없는 라이브 데이터가 대부분 수동 검토로 이동했다. 2일차에는 다음 조건을 만족하는 경우 자동 승인할 수 있도록 규칙을 세분화했다.

- 네이버 후보 상호가 원본 상호와 강하게 일치한다.
- 후보 카테고리가 음식점, 카페, 주점 계열이다.
- 네이버 후보 주소가 부산에 속한다.
- 좌표가 존재한다.
- 지출 목적이 간담, 오찬, 만찬, 식사, 다과, 커피 등 음식 소비 맥락이다.

단, 짧고 일반적인 상호명은 여전히 보수적으로 처리한다. 예를 들어 `씨드`처럼 짧은 주소 없는 후보는 바로 승인하지 않고 수동 검토 대상으로 남긴다. 반면 `오복정`, `토곡정`처럼 네이버 후보와 정확히 일치하고 부산 주소와 좌표가 확인되는 경우는 공공 인허가 데이터가 다른 주소를 반환하더라도 네이버 후보를 우선할 수 있게 했다.

### 지점명 및 상호명 정규화 개선

업무추진비 원본에는 `본도시락 시청점외 1`, `19버거테이블 외 1`처럼 실제 상호명 뒤에 동행 건수나 부가 설명이 붙는 경우가 있다. 이를 위해 상호명 정제 로직을 추가했다.

개선된 처리 내용은 다음과 같다.

- `외 1`, `외 2` 같은 동행/복수 표기를 검색어에서 제거
- `일원`, `등` 같은 모호한 접미 표현 제거
- `주식회사`, `유한회사`, `㈜`, `(주)` 같은 법인 표기 제거
- `시청점`, `부산시청점`, `해운대점`, `서면점`, `본점` 등 지점 힌트 기반 유사도 보정
- 공백 제거 버전과 정규화 버전을 모두 별칭 후보로 생성

이 변경으로 네이버 검색 쿼리 품질이 좋아졌고, 지점명이 조금 다르게 표기된 경우에도 같은 장소로 판단할 가능성이 높아졌다.

### 비음식 지출 사전 필터링 추가

음식점 상호와 같은 문자열이 있더라도 지출 목적이 음식 소비가 아닌 경우 자동으로 제외하도록 목적 기반 거절 규칙을 추가했다.

현재 자동 거절되는 목적 예시는 다음과 같다.

```text
기념품
사무용품
문구
비품
소모품
홍보물품
격려물품
필요물품
특산품
```

다만 `회의 다과 구입`, `직원 격려 간식 구입`처럼 실제 음식 구매 맥락이 있는 경우는 비음식 지출로 오판하지 않도록 예외를 두었다.

이 규칙은 별칭 기억보다 먼저 적용된다. 즉, 과거에 승인된 음식점 이름이 지출처로 등장하더라도 목적이 `시정홍보 방문기념품 구입`이면 기존 음식점에 연결하지 않고 `NON_FOOD_PURPOSE_GIFT` 사유로 거절한다.

### 인허가 데이터 충돌 처리 개선

공공 인허가 데이터가 항상 정확한 후보를 반환하지 않는 경우를 고려해 충돌 처리 규칙을 개선했다.

예를 들어 네이버 후보는 부산 음식점으로 정확히 잡히지만, 인허가 API가 다른 지역이나 다른 도로명 주소의 같은 상호를 반환할 수 있다. 이 경우 도로명, 부산 포함 여부, 후보 주소 유사도를 비교해 인허가 주소가 네이버 후보와 충돌한다고 판단하면 네이버 고신뢰 후보를 우선할 수 있도록 했다.

이 변경은 주소 없는 실제 업무추진비 행에서 불필요한 수동 검토를 줄이기 위한 조치다. 단, 자동 승인 조건은 상호명 정확도, 음식 카테고리, 부산 주소, 음식 소비 목적을 함께 만족해야 한다.

### 재검증 흐름 개선

수동 검토로 남아 있던 후보를 나중에 다시 검증할 수 있는 `verify_pending` 흐름을 보강했다.

주요 개선 내용은 다음과 같다.

- `verify_pending` 실행 시 별칭 기억과 비음식 목적 규칙을 함께 적용
- 애매했던 `place_verifications` 레코드를 성공 상태로 업데이트 가능
- 수동 검토 task가 자동 승인 또는 자동 거절되면 reason을 함께 갱신
- 재검증 후 지도 노출 대상 음식점으로 연결 가능
- 최근 검증 작업 현황에 `verify_pending`, `alias_memory_recheck`, `purpose_rule_recheck` 유형을 포함

운영 스크립트로는 `scripts/verify_pending.py`가 추가되어, 대기 중인 후보를 제한 개수만큼 재검증하고 전후 상태를 JSON으로 출력할 수 있다.

## 3. 테스트 보강

2일차에 테스트가 크게 늘었다. 1일차 기준 전체 테스트는 14개였고, 2일차 기준 전체 테스트는 30개다.

추가 검증된 주요 케이스는 다음과 같다.

- 주소 없는 고신뢰 네이버 후보 자동 승인
- 짧고 일반적인 주소 없는 후보는 수동 검토 유지
- 수동 검토 후보 재검증 후 성공 상태 업데이트
- 별칭 기억을 통한 반복 상호 자동 승인 및 기존 지도 항목 연결
- 비음식 목적 지출이 별칭 기억보다 먼저 거절되는지 확인
- 지점명 힌트 기반 상호 매칭
- 공공 인허가 없이도 고신뢰 네이버 후보를 제한적으로 승인하는 케이스
- 인허가 주소가 충돌할 때 네이버 정확 후보를 우선하는 케이스
- `회의 다과`, `직원 격려 간식`을 비음식 지출로 잘못 거절하지 않는 예외 처리
- 네이버 검색어에서 `외 1` 같은 부가 표현 제거

전체 테스트 결과는 다음과 같다.

```text
Ran 30 tests in 1.413s
OK
```

샌드박스 내부에서는 로컬 HTTP 서버 테스트 2개가 `127.0.0.1` 임시 포트 바인딩 권한 문제로 실패했다. 동일 명령을 권한 밖에서 실행했을 때 전체 테스트가 통과했으므로, 현재 확인된 실패 원인은 코드 문제가 아니라 실행 환경 제한이다.

## 4. 구현 관점의 의미

2일차 변경의 핵심은 검증 파이프라인이 단순한 “외부 API 조회 결과 저장”에서 “공공데이터 특유의 노이즈를 흡수하는 판단 시스템”으로 한 단계 이동했다는 점이다.

업무추진비 데이터는 사람이 작성한 표 기반 데이터라 다음 문제가 자주 발생한다.

- 주소가 비어 있다.
- 상호명에 `외 1`, `등`, 지점명이 섞인다.
- 실제 음식점 이름과 법인명 또는 결제처명이 다르다.
- 공공 인허가 API가 같은 상호의 다른 지점이나 다른 지역 결과를 반환한다.
- 음식점 이름이 있어도 실제 지출 목적은 기념품, 물품, 사무용품일 수 있다.

이번 변경은 이 문제들을 각각 규칙과 테스트로 분리해 처리했다. 특히 자동 승인 범위를 넓히면서도 짧은 상호명, 목적 불일치, 주소 충돌 같은 위험 케이스는 별도로 제한했다는 점이 중요하다.

## 6. 다음 개발 과제

### 라이브 데이터 기반 검증

- 실제 부산 업무추진비 게시판에서 수집한 XLSX 샘플을 더 늘린다.
- 주소 없는 행이 자동 승인되는 비율과 오승인 가능성을 확인한다.
- 별칭 기억으로 연결된 후보가 실제로 동일 장소인지 표본 검수한다.
- 공공 인허가 API의 실제 응답이 네이버 후보와 얼마나 자주 충돌하는지 기록한다.

### 관리자 검토 화면 개선

- 후보별 reason code를 운영자가 이해할 수 있는 문장으로 변환한다.
- 네이버 후보, 인허가 스냅샷, 원본 지출 행을 한 화면에서 비교할 수 있게 한다.
- 별칭 기억으로 자동 승인된 케이스도 감사 로그에서 확인할 수 있게 한다.

### 운영 품질 보강

- `verify_pending` 실행 결과를 배치 히스토리에서 추적하기 쉽게 만든다.
- alias memory가 잘못 학습된 경우 되돌리거나 비활성화하는 관리 기능을 추가한다.
- 자동 승인 기준값을 설정값으로 분리할지 검토한다.
- 라이브 데이터에서 발견된 실패 케이스를 테스트 fixture로 계속 누적한다.

## 7. 한 줄 결론

2일차 개발에서는 지도 서비스의 겉모습보다 데이터 신뢰도를 높이는 작업이 진행되었다. 별칭 기억, 주소 없는 후보 승인, 비음식 목적 필터, 재검증 흐름이 추가되면서 실제 공공데이터를 운영 가능한 지도 데이터로 바꾸는 검증 파이프라인의 완성도가 크게 올라갔다.
