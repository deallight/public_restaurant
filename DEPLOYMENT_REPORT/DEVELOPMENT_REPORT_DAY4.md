## 2. 핵심 개선 사항

### 라이브 수집과 검증 단계 분리

기존 `run-busan-live`는 라이브 데이터를 수집한 뒤 곧바로 검증 흐름에 태우는 구조였다. 4일차에는 실제 부산시 데이터를 다룰 때 수집과 검증을 분리했다.

변경된 흐름은 다음과 같다.

```text
실제 부산시 수집
→ 원본 문서 및 지출 행 저장
→ 후보는 PENDING_VERIFICATION 상태로 보류
→ 별도 "수집 데이터 검증" 작업에서 초기 미검증 후보만 처리
→ 이후 일반 "수동 검토 재검증"으로 운영 검토 대상 재처리
```

이 구조의 목적은 라이브 수집 과정에서 외부 API 호출, 후보 검증, 관리자 검토가 한 번에 섞이지 않게 하는 것이다. 수집량이 늘어나도 먼저 원본 데이터를 안정적으로 확보하고, 검증은 별도 배치로 제어할 수 있다.

### `verify_collected` 배치 추가

새로운 `verify_collected` 흐름을 추가했다. 이 배치는 `PENDING_VERIFICATION` 상태의 초기 미검증 후보만 처리한다.

기존 `verify_pending`과의 차이는 다음과 같다.

- `verify_collected`: 라이브 수집 직후 아직 검증되지 않은 후보만 처리
- `verify_pending`: 일반 수동 검토 대기 후보를 재검증

`verify_collected`는 다음 조건의 후보를 대상으로 한다.

```text
verification_status = not_requested
review_note = PENDING_VERIFICATION
status = needs_review
manual_review_status = pending
manual_review_task가 없거나 pending 상태
```

배치 summary에는 `pending_before`, `pending_after`, `rows_processed`가 포함되어 검증 대기량 변화를 확인할 수 있다.

### 라이브 수집 조건 제어 추가

관리자 화면에서 실제 부산시 수집 조건을 지정할 수 있게 했다.

추가된 입력값은 다음과 같다.

```text
시작일
종료일
페이지 수
최대 문서 수
```

서버 API도 같은 payload를 받는다.

```text
POST /ops/run-busan-live
{
  "start_date": "2026-01-01",
  "end_date": "2026-06-13",
  "max_pages": 2,
  "max_documents": 20
}
```

`BusanCityLiveAdapter`는 XLSX에서 추출한 사용일 기준으로 날짜 범위를 필터링한다. 첨부파일 다운로드 실패나 일부 게시글 접근 실패가 발생해도 전체 수집이 중단되지 않도록 예외 처리를 보강했다.

## 3. 후보 데이터 관리 기능

### 후보 보정 필드 추가

`restaurant_candidates`에 관리자 보정 필드를 추가했다.

```text
review_place_name
review_normalized_place_name
review_address
review_normalized_address
review_major_category
```

원본 데이터는 그대로 보존하고, 운영자가 검토 과정에서 보정한 상호명, 주소, 분류를 별도 필드에 저장한다. 서비스 계층에서는 `effective_*` 값을 계산해 보정값이 있으면 보정값을 우선 사용하고, 없으면 원본값을 사용한다.

기존 SQLite DB에도 적용될 수 있도록 `Database.initialize()` 단계에서 누락 컬럼을 추가하는 경량 마이그레이션을 넣었다.

### 후보 목록 API 추가

관리자용 후보 목록 API를 추가했다.

```text
GET /admin/candidates
```

지원 기능은 다음과 같다.

- 상태별 그룹 조회: `needs_review`, `verified`, `rejected`
- 그룹별 독립 offset pagination
- 검색: 상호명, 주소, 기관, 부서, 목적, 문서명
- 정렬: ID 최신순/오래된순, 최근 수정순, 사용일 최신순, 금액 높은순, 상호명순
- provider 후보 최대 10개 반환
- 원본값과 보정값을 함께 반환

기존 수동 검토 큐가 “대기 항목만 보는 화면”이었다면, 새 후보 목록은 승인/반려/검토 상태 전체를 관리하는 운영 테이블에 가깝다.

### 후보 직접 편집 및 상태 전환

관리자는 후보별로 다음 값을 직접 수정할 수 있다.

- 보정 상호명
- 보정 주소
- 보정 분류
- 상태: 수동검토, 승인, 반려
- 반려 사유
- 검토 의견

API는 다음과 같다.

```text
POST /admin/candidates/{candidate_id}
```

상태 전환 동작은 다음과 같다.

- `needs_review`: 후보를 다시 수동 검토 상태로 둔다.
- `verified`: 보정값 기준으로 음식점 레코드를 만들거나 갱신하고 지도 노출 상태로 만든다.
- `rejected`: 후보를 반려 처리하고 기존 음식점 링크가 있으면 제거한다.

승인된 후보를 다시 반려로 옮길 수 있도록 링크 제거와 지도 숨김 처리도 구현했다. 후보 링크가 제거된 음식점에 더 이상 연결된 지출 행이 없으면 `map_exposure_status = hidden`으로 전환한다.

### 후보 지오코딩 버튼 추가

관리자 후보 화면에 `지오코딩` 버튼을 추가했다.

API는 다음과 같다.

```text
POST /admin/candidates/{candidate_id}/geocode
```

동작 방식은 다음과 같다.

- 보정 상호명/주소/분류를 먼저 저장한다.
- 네이버 Maps Geocoding client가 설정되어 있으면 주소를 좌표로 변환한다.
- 변환 결과를 `place_verifications`에 `provider = naver_geocode`로 저장한다.
- 이후 후보를 승인하면 해당 좌표를 사용해 음식점 레코드를 만들 수 있다.

지오코딩이 별도 버튼으로 분리된 이유는 관리자가 주소 보정만 하고 좌표 변환은 필요할 때 실행할 수 있게 하기 위해서다.

### provider 후보 새로고침

후보 보정값을 저장할 때 네이버 검색 client가 설정되어 있으면 보정된 상호명/주소 기준으로 provider 후보를 다시 조회하고 `place_verifications`에 저장한다.

이로써 원본 상호명이 부정확한 경우에도 운영자가 보정 상호명과 주소를 입력한 뒤 네이버 후보를 새로 만들 수 있다.

## 4. 관리자 UI 개선

### 후보 데이터 중심 화면으로 재구성

관리자 화면의 `수동 검토` 섹션을 `후보 데이터` 섹션으로 확장했다. 이제 단순 대기열이 아니라 후보 상태 전체를 상태별 그룹으로 볼 수 있다.

화면 구성은 다음과 같다.

- 검색 입력
- 상태별 접이식 그룹
- 그룹별 페이지네이션
- 정렬 select
- 후보별 원문 정보
- 보정값 입력 필드
- provider 후보 가로 스크롤 목록
- 지오코딩 버튼
- DB 업데이트 버튼

상태별 그룹은 다음과 같다.

```text
수동검토
승인
반려
```

각 그룹은 독립 페이지 offset을 가지므로 승인 목록을 넘기더라도 수동검토 목록의 페이지 위치가 영향을 받지 않는다.

### 라이브 수집 컨트롤 추가

관리자 화면 상단에 실제 부산시 수집 조건 입력 UI를 추가했다.

```text
시작일: 2026-01-01
종료일: 2026-06-13
페이지: 2
최대 문서: 20
```

버튼 구성도 다음처럼 정리했다.

```text
실제 부산시 수집
수집 데이터 검증
수동 검토 재검증
Fixture 배치
```

배치 결과 표시도 수집 작업과 검증 작업을 구분해 보여준다. 검증 작업은 `검증 대기 before→after`, `처리`, `승인`, `수동검토`, `반려`, `DLQ`를 표시한다.

## 5. 네이버 검색 및 라이브 수집 안정성 개선

### 네이버 후보 정렬 개선

네이버 지역 검색 결과를 단순 최초 결과 기준으로 사용하지 않고, 주소 유사도, 부산 주소 여부, 이름 유사도 기준으로 정렬한다.

정렬 기준은 다음과 같다.

```text
주소 유사도
부산 주소 bonus
이름 유사도
```

또한 검색 쿼리에 주소 단독 검색도 추가하고, 반환 후보 수를 최대 10개로 늘렸다. 관리자 화면에서 후보를 비교하고 선택하기 위한 변경이다.

### 라이브 어댑터 예외 처리 강화

부산시 게시판 수집 중 일부 페이지, 상세 문서, 첨부파일에서 오류가 발생해도 전체 수집이 중단되지 않도록 했다.

주요 변경은 다음과 같다.

- 목록 페이지 접근 실패 시 해당 페이지 skip
- 상세 페이지 파싱 실패 시 해당 문서 skip
- 첨부파일 다운로드 실패 시 문서는 유지하고 attachments는 빈 상태로 처리
- 첨부 다운로드는 짧은 retry 적용
- XLSX 사용일 기준 날짜 범위 필터 적용

이 변경은 실제 공공기관 게시판 수집에서 발생하기 쉬운 네트워크/첨부파일 오류를 흡수하기 위한 것이다.

## 8. 리스크 및 다음 과제

### PostgreSQL 스키마 반영 필요

SQLite 스키마에는 후보 보정 필드가 추가되었고 경량 마이그레이션도 들어갔다. 운영용 PostgreSQL 스키마에도 동일 필드와 마이그레이션 절차를 반영해야 한다.

### 관리자 지오코딩 UX 검증 필요

지오코딩 버튼과 DB 업데이트 버튼이 분리되었으므로, 운영자가 어떤 순서로 작업해야 하는지 실제 사용 흐름을 점검해야 한다. 지오코딩 결과가 없는 경우, 실패한 경우, 주소가 잘못된 경우의 UI 피드백도 더 명확히 할 필요가 있다.

### 라이브 수집 대량 실행 검증 필요

페이지 수와 문서 수를 늘렸을 때 부산시 게시판 응답 속도, 첨부 다운로드 실패율, XLSX 양식 다양성을 확인해야 한다. 특히 `verify_collected`를 분리한 구조가 실제 대량 수집에서 적절한지 운영 로그로 확인해야 한다.

### 후보 상태 전환 감사/복구 기능 보강

승인된 후보를 반려로 되돌릴 수 있게 되었지만, 운영 중 잘못된 상태 전환을 되돌리는 명시적 복구 UI는 아직 부족하다. audit log 기반 복구 또는 변경 이력 조회 화면이 필요하다.

### 관리자 화면 시각 검증 필요

후보 편집 UI가 상당히 복잡해졌으므로 브라우저에서 실제 레이아웃을 확인해야 한다. 특히 모바일/좁은 화면에서 후보 DB 행, provider 후보 가로 스크롤, 페이지네이션이 겹치지 않는지 점검해야 한다.

## 9. 한 줄 결론

4일차 개발에서는 서비스가 단순 자동 검증 MVP를 넘어, 실제 운영자가 수집 데이터와 후보 DB를 직접 관리할 수 있는 내부 운영 도구에 가까워졌다. 라이브 수집과 검증을 분리하고, 후보 보정/지오코딩/상태 전환/검색/페이지네이션을 추가하면서 운영 가능한 데이터 정제 흐름의 기반이 마련되었다.
