# 공공기관 업무추진비 맛집 지도 서비스 개발 진행 보고서

작성일: 2026-06-04

## 1. 프로젝트 개요

공공기관의 업무추진비 집행 내역에서 실제 음식점 방문 데이터를 추출하고, 이를 지도 기반으로 탐색할 수 있는 MVP를 개발하고 있다. 현재 범위는 부산광역시 v1이며, Python 표준 라이브러리 기반 HTTP 서버와 개발 DB를 중심으로 구성했다.

서비스의 핵심 목표는 단순한 지출 목록 조회가 아니라, 공개된 업무추진비 데이터를 수집, 정규화, 검증한 뒤 사용자가 지도와 랭킹, 검색 기능으로 확인할 수 있게 만드는 것이다. 운영 환경을 염두에 둔 PostgreSQL/PostGIS 스키마도 별도로 준비되어 있어, MVP 이후 실서비스 전환을 고려한 구조로 설계되어 있다.

## 2. 현재까지 구현된 주요 기능

### 데이터 수집 및 파이프라인

- 부산광역시 업무추진비 게시판을 대상으로 한 수집 어댑터를 구현했다.
- 로컬 개발과 테스트를 위한 fixture 기반 어댑터를 함께 제공한다.
- 원본 문서, 지출 행, 음식점 후보, 검증 결과, 음식점 방문 링크가 중복 저장되지 않도록 idempotent 파이프라인을 구성했다.
- XLSX 첨부파일에서 업무추진비 지출 행을 추출하는 파서를 구현했다.
- 일일 수집 작업 실행 스크립트와 운영용 API 엔드포인트를 마련했다.

### 음식점 검증 로직

- 네이버 지역 검색, 네이버 지도 지오코딩, 공공데이터포털 인허가 데이터를 연결할 수 있는 통합 클라이언트를 구현했다.
- 테스트 환경에서는 실제 외부 API를 호출하지 않도록 fake client를 사용한다.
- 장소명, 주소 유사도, 인허가 상태, 카테고리를 종합해 음식점 후보를 자동 승인, 거절, 수동 검토 대상으로 분류한다.
- AI 역할은 DB에 직접 쓰지 않고 `VerificationDecision` 제안만 반환하도록 경계를 분리했다.
- 주소가 없는 라이브 데이터나 애매한 후보는 바로 승인하지 않고 관리자 검토 큐로 보낸다.

### 공개 사용자 기능

- 공개 지도 화면을 제공한다.
- 네이버 지도 키가 있으면 네이버 지도 JS API를 시도하고, 없으면 로컬 fallback 지도를 사용한다.
- 음식점 지도 목록 API를 구현했다.
- 음식점 상세 조회, 랭킹, 검색 API를 구현했다.
- 음식점 리뷰 작성 기능을 구현했다.
- 리뷰 도배 방지를 위해 동일 음식점 기준 동일 사용자/IP 해시의 시간당 작성 수를 제한한다.
- 부적절한 리뷰 신고 API를 구현했다.

### 관리자 및 운영 기능

- 관리자 화면 진입점을 구현했다.
- 수동 검토 큐 조회 기능을 구현했다.
- 후보 승인, 기존 음식점 병합, 후보 거절 API를 구현했다.
- 리뷰 신고 목록 조회 기능을 구현했다.
- 계정 병합 API를 구현했다.
- 일일 파이프라인 실행 및 배치 상태 조회 API를 구현했다.
- 수집 출처 registry 조회 API를 구현했다.

### 데이터베이스 설계

- 개발 스키마와 초기화/롤백 흐름을 구현했다.
- 운영용 PostgreSQL 스키마를 별도 SQL로 정리했다.
- PostgreSQL 확장으로 `pg_trgm`, `postgis` 사용을 전제로 설계했다.
- 지역, 기관, 원본 문서, 지출 기록, 음식점 후보, 장소 검증, 음식점, 리뷰, 감사 로그 등 핵심 도메인 테이블을 분리했다.
- 운영 앱 확장 SQL, 뷰, seed region 데이터, schema check SQL을 함께 준비했다.

## 4. 기술 구조

현재 MVP는 의존성을 최소화하기 위해 Python 표준 라이브러리를 중심으로 구현되어 있다.

- 서버: Python `http.server` 기반 Threading HTTP server
- 개발·운영 DB: PostgreSQL
- 운영 DB 설계: PostgreSQL + PostGIS + pg_trgm
- 지도: 네이버 지도 JS API 또는 로컬 fallback 지도
- 외부 연동: 네이버 Search, 네이버 Maps Geocoding, 네이버/Google OAuth, 공공데이터포털 인허가 API
- 테스트: Python `unittest`

이 구조의 장점은 초기 배포와 검증 비용이 낮고, 외부 API 키가 없는 환경에서도 기능 확인이 가능하다는 점이다. 동시에 운영 스키마는 별도로 준비되어 있어 실제 서비스 전환 시 데이터 모델을 확장하기 쉽다.

## 5. 테스트 및 검증 결과

전체 테스트를 실행한 결과 14개 테스트가 모두 통과했다.

```text
Ran 14 tests in 1.271s
OK
```

검증된 주요 항목은 다음과 같다.

- 일일 파이프라인 중복 실행 시 데이터가 중복 저장되지 않는지 확인
- 개발 스키마 초기화 및 개발용 롤백 동작 확인
- 음식점 후보 자동 승인, 거절, 수동 검토 분기 확인
- 주소가 없는 라이브 행이 관리자 검토로 이동하는지 확인
- 공공데이터포털 인허가 API 응답 매핑 확인
- 공개/관리자/운영 HTTP API 동작 확인
- 리뷰 작성 제한 및 상태 코드 확인
- 서비스 계층의 검색, 랭킹, 리뷰 신고, 관리자 처리 로직 확인

처음 샌드박스 환경에서 테스트를 실행했을 때 HTTP 서버 테스트 2개가 로컬 포트 바인딩 권한 문제로 실패했지만, 권한 밖에서 동일 테스트를 다시 실행한 결과 전체가 통과했다. 따라서 현재 실패 원인은 코드 문제가 아니라 실행 환경의 네트워크 바인딩 제한으로 판단된다.

## 6. 현재 상태 요약

현재 저장소는 아직 첫 커밋 전 상태이며, 전체 파일이 신규 추가된 상태다. 구현 관점에서는 MVP의 뼈대가 대부분 갖춰져 있다.

완료된 영역은 다음과 같다.

- 부산광역시 v1 데이터 수집 흐름
- 업무추진비 XLSX 파싱
- 음식점 후보 정규화 및 검증
- 공개 지도/검색/랭킹 API
- 리뷰 작성 및 신고
- 관리자 검토 큐
- 운영 배치 실행 API
- 개발 DB 및 운영 DB 스키마
- 테스트 커버리지 기본 구성

남은 핵심 작업은 실제 API 키와 라이브 데이터로 운영 검증을 진행하고, 프론트엔드 사용성을 다듬고, 배포 환경을 정하는 것이다.

## 7. 다음 개발 계획

### 1단계: 라이브 데이터 검증 강화

- 공공데이터포털 serviceKey를 주입해 인허가 API 실데이터 응답을 확인한다.
- 부산 구군별 데이터 편차와 주소 필드 품질을 점검한다.
- 네이버 Search/Maps 응답과 공공 인허가 데이터의 매칭 기준을 실제 샘플 기준으로 조정한다.
- 실패 케이스를 fixture로 추가해 회귀 테스트를 보강한다.

### 2단계: 관리자 검토 UX 개선

- 수동 검토 대상의 원본 지출 행, 후보 장소, 인허가 근거를 한 화면에서 비교할 수 있게 개선한다.
- 승인, 병합, 거절 작업 후 다음 항목으로 자연스럽게 이동하는 흐름을 만든다.
- 검토 사유와 감사 로그를 운영자가 이해하기 쉬운 문구로 정리한다.

### 3단계: 공개 지도 화면 고도화

- 지도 마커와 리스트 연동을 더 부드럽게 만든다.
- 카테고리, 지역, 기간 필터를 사용자가 빠르게 조합할 수 있게 개선한다.
- 음식점 상세 화면에서 방문 내역, 총액, 리뷰, 출처 근거를 더 명확히 보여준다.
- 모바일 화면에서 지도와 목록 전환 UX를 점검한다.

### 4단계: 배포 준비

- 운영 DB 마이그레이션 절차를 정리한다.
- 환경변수 기반 비밀값 주입 방식을 배포 환경에 맞게 확정한다.
- 일일 배치 실행 방식을 cron 또는 별도 scheduler로 구성한다.
- 장애 시 재시도, 실패 배치 확인, 원본 문서 재처리 절차를 문서화한다.

## 8. 리스크 및 확인 필요 사항

- 부산 업무추진비 게시판의 HTML 구조가 바뀌면 live crawler 수정이 필요할 수 있다.
- 일부 XLSX 양식은 기관 또는 기간별로 열 이름과 병합 셀 구조가 다를 수 있다.
- 음식점명이 축약되거나 주소가 비어 있는 경우 자동 검증 정확도가 낮아질 수 있다.
- 공공데이터포털 인허가 endpoint의 실제 응답 필드와 제한 정책은 serviceKey로 라이브 검증이 필요하다.
- 네이버 지도/검색 API 사용량 제한과 비용 정책을 배포 전에 확인해야 한다.

## 9. 한 줄 결론

현재 프로젝트는 “부산 업무추진비 데이터를 음식점 지도 서비스로 변환하는 MVP”의 핵심 파이프라인과 API, 관리자 검토 흐름, 테스트 기반이 완성된 상태다. 다음 단계에서는 실제 외부 API와 라이브 데이터를 붙여 검증 정확도를 높이고, 공개 지도와 관리자 화면의 사용성을 끌어올리는 작업이 중요하다.
